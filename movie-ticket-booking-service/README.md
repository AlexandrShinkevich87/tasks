# Кинотеатр: Java 21, коллекции и многопоточность

Первый учебный этап сервиса заказа билетов. Код пишет и показывает ментор.
Все данные хранятся в памяти одного процесса. Уведомления имитируются и сохраняются в журнале отправщика:
реальные email не отправляются. БД, Kafka, Spring и внешние сервисы не нужны.
На этом этапе приложение запускается как консольная демонстрация. Spring и HTTP появятся на следующем занятии.

## Быстрый запуск

Требуются JDK 21 и Maven 3.9+. Команды выполняются из корня проекта:

```powershell
mvn verify
java -jar target/movie-ticket-booking-service-1.0-SNAPSHOT.jar
```

Без аргументов запускается полный демонстрационный сценарий; также допустим аргумент `--demo`.
Приложение завершает работу после покупок и обработки уведомлений.

Для PowerShell подготовлены короткие команды:

```powershell
.\scripts\verify.ps1
.\scripts\run.ps1
```

В IntelliJ IDEA открыть корневой `pom.xml` как Maven-проект и выбрать SDK 21.
Точка входа — `ru.mentoring.cinema.CinemaApplication`.

## Сбор исходников любого проекта

Скрипт `scripts/collect-project.sh` запускается в Bash, в том числе Git Bash на Windows:

```bash
# Текущий проект: результат movie-ticket-booking-service-sources.txt в его корне.
bash scripts/collect-project.sh

# Другой проект: результат <имя-проекта>-sources.txt в его корне.
bash scripts/collect-project.sh "/path/to/another project"

# Свой путь к результату; относительный путь считается от текущего каталога запуска.
bash scripts/collect-project.sh "/path/to/another project" "./collected-sources.txt"
```

Собираются текстовые исходники, конфигурация сборки, документация и скрипты без ограничения
по языку программирования. Каталоги `target` исключаются на любой глубине, включая вложенные
Maven-модули. Также пропускаются служебные каталоги, результаты сборки, зависимости и бинарные файлы.
Файл результата и временный файл не включаются в сборку. Готовый результат заменяется после
успешного завершения сбора. Список параметров: `bash scripts/collect-project.sh --help`.

## Что показывает демонстрация

1. Афишу из двух текущих фильмов с сортировкой.
2. Расписание и 15 кресел зала; дата сеанса вычисляется как завтра в зоне кинотеатра.
3. Покупку двух мест одним заказом и повтор обращения с тем же ключом.
4. Сто покупателей, одновременно претендующих на одно кресло: 1 покупка, 99 конфликтов.
5. Еще сто покупателей на оставшиеся 12 кресел: 12 покупок, 88 конфликтов.
6. Поиск заказа по номеру и поиск заказов по критериям.
7. Независимую обработку очереди двумя потоками уведомлений.

В конце: 15 проданных мест, 14 заказов, 14 успешных уведомлений.
Номера заказов и распределение работы между потоками меняются от запуска к запуску.
Демонстрация ждет завершения уведомлений и завершает все executors.

## Структура проекта

Один Maven-проект с одним `pom.xml`. Исходники находятся в `src/main/java`,
тесты — в `src/test/java`, настройки логирования — в `src/main/resources`.

```text
src/main/java/ru/mentoring/cinema/
├── CinemaApplication.java
├── CinemaRuntime.java
├── model/
├── service/
├── storage/
├── notification/
└── demo/
```

| Пакет | Ответственность |
| --- | --- |
| ru.mentoring.cinema | Точка входа и создание объектов приложения |
| model | Все модели: фильмы, сеансы, заказы, афиша, сортировки, уведомления, результаты и проверки значений |
| service | BookingService и CatalogueService: покупка, поиск, афиша и расписание |
| storage | InMemoryCatalogue, InMemoryBookingStore и SampleCatalogue: данные и очередь на коллекциях |
| notification | NotificationDispatcher и RecordingNotificationSender: обработка очереди и имитация отправки |
| demo | CinemaDemo и ConcurrentCustomers: полный сценарий и одновременные покупатели |

`CinemaRuntime` создает конкретные классы и передает их через конструкторы.
Собственных интерфейсов в проекте нет. JavaDoc на русском объясняют классы и методы прямо в IDE.
Все модели, включая record и enum, находятся в отдельных файлах пакета model.
Например, Status, SortField, Sort, MovieListing и SessionView используются CatalogueService,
а Delivery и Report описывают результаты уведомлений.
Имена методов описывают действие: `findScreeningById` ищет сеанс и возвращает Optional,
`getOrderById` получает заказ или сообщает об отсутствии, `purchaseTickets` оформляет покупку,
`sendOrderConfirmation` отправляет подтверждение, `awaitProcessedNotifications` ожидает обработку событий.
Методы record, например `order.id()` и `session.screening()`, читают соответствующие поля модели.

## Где структуры данных решают бизнес-задачу

| Структура | Класс | Для чего |
| --- | --- | --- |
| List / ArrayList | BookingRequest, CatalogueService, ConcurrentCustomers | Выбранные места, выдача фильмов, список задач/результатов; порядок имеет значение |
| HashSet | BookingRequest, InMemoryBookingStore | Обнаружение дублей во входе и быстрый поиск проданных мест |
| LinkedHashMap | InMemoryCatalogue, InMemoryBookingStore | Поиск по ID и предсказуемый порядок обхода каталога/заказов |
| HashMap | InMemoryBookingStore | Идемпотентные обращения, индекс занятости по сеансам |
| TreeMap | InMemoryCatalogue | Индекс сеансов по времени: хронологический обход без пересортировки всего расписания |
| TreeSet | SampleCatalogue | Построение упорядоченной схемы кресел по ряду и номеру |
| ArrayBlockingQueue | InMemoryBookingStore | Ограниченная FIFO-очередь событий для отправки уведомлений |
| ConcurrentHashMap | RecordingNotificationSender | Журнал результатов, который одновременно изменяют несколько отправщиков |
| Comparator / Stream API | CatalogueService, BookingService | Несколько ключей сортировки, фильтры, группировка и расчет популярности |

Хеш-коллекции дают средний O(1) поиск, TreeMap/TreeSet — O(log n) операции.
Фильтрация списков здесь выполняется обходом, сортировка выдачи — O(n log n).
`Seat` — неизменяемый record: ключи в HashSet не изменяются после добавления.
Все выдаваемые списки/наборы — снимки или неизменяемые копии.

## Атомарная покупка

Сначала сервис проверяет фильм, локальную дату сеанса и принадлежность кресел залу.
Затем `InMemoryBookingStore.confirmPurchase` выполняет под одним `ReentrantLock`:

1. Поиск пары customerId + requestId. Точный повтор возвращает прежний заказ.
2. При другом содержимом под тем же ключом — REQUEST_CONFLICT.
3. Проверку всех выбранных кресел в HashSet.
4. Создание снимка заказа, включая проверку начала сеанса через Clock.
5. Неблокирующую постановку события в ограниченную очередь.
6. Запись всего заказа, всех мест и результата обращения.

До успешной проверки/постановки события состояние продажи не меняется.
Если занято хотя бы одно место, не продается ни одно из остальных мест заказа.
Если очередь заполнена — QUEUE_FULL, без заказа и без занятых кресел.
Все постановки событий продаж сериализованы тем же lock; сам отправщик работает вне lock.

Consumer может извлечь событие раньше освобождения lock, но чтение заказа также использует этот lock.
Поэтому consumer увидит уже сохраненный заказ. Медленная отправка не удерживает блокировку покупки.

ConcurrentHashMap сама по себе не сделала бы последовательность «проверить → сохранить несколько мест →
создать заказ → поставить событие» атомарной.

Одна блокировка выбрана для наглядности. Она действует только в одном процессе.
Это не распределенная блокировка и не постоянная транзакция. После перезапуска все данные исчезают.

## Потоки и доставка

Покупатели в демонстрации — Java 21 virtual threads. CountDownLatch служит общим стартовым барьером.
Критерий правильности — результат и состояние хранилища, а не очередность планирования потоков.

NotificationDispatcher использует отдельный фиксированный пул `notification-1`, `notification-2`.
FIFO определяет порядок извлечения, но при нескольких workers завершения могут переставляться.
До трех попыток отправки, ограниченный backoff; исчерпанные ошибки видны в отчете.
Сбой отправщика не отменяет уже оформленный заказ.

RecordingNotificationSender имитирует идемпотентного провайдера по eventId.
Это не обещание exactly-once для реального email: внешний провайдер в следующем этапе потребует
собственного механизма идемпотентности. В текущем процессе повтор покупки не создает второе событие.

При остановке нужно сначала прекратить покупки, затем закрыть dispatcher.
Он пытается завершить накопленную работу, после пяти секунд принудительно прерывает зависшие workers.
Очередь не переживает аварийную остановку и не является надежным outbox.

## Сценарии без HTTP

Вызовы из `CinemaDemo` проходят через обычные Java-методы:

| Метод | Назначение |
| --- | --- |
| CatalogueService.findMoviesForPoster | Афиша: текущие/будущие фильмы, фильтр жанра, сортировка по нескольким полям |
| CatalogueService.findScreeningsByMovieCityAndDate | Расписание фильма в городе на локальную дату кинотеатра |
| CatalogueService.buildSessionView | Сеанс, зал и доступные кресла |
| BookingService.purchaseTickets | Атомарная покупка выбранных мест с защитой от повторов |
| BookingService.getOrderById | Снимок покупки по UUID заказа |
| BookingService.findOrdersByFilter | Заказы за период, по фильму и списку клиентов |
| InMemoryBookingStore.getNotificationReport | Состояние очереди и результаты отправки уведомлений |

В BookingRequest обязательны requestId, клиент с телефоном/email, movieId, date, screeningId и seats.
Дата/фильм сверяются с сеансом, цену рассчитывает сервис. Дубли мест отклоняются, а не удаляются.
Одинаковый requestId действует в пределах customerId; изменение порядка списка мест считается изменением запроса.

Популярность — число подтвержденных билетов за время жизни процесса. День афиши определяется
в Asia/Almaty, как и даты тестового каталога. У фильма несколько жанров: фильтр проверяет
наличие жанра, сортировка использует первый жанр по алфавиту. ID служит последним критерием сортировки.
Период поиска заказов применяется к createdAt как [from, to); между фильтрами AND, внутри customerIds — IN.
Платежи, временные брони, отмены/возвраты пока не моделируются.

## Логирование

`CinemaDemo` использует SLF4J: `LoggerFactory.getLogger(CinemaDemo.class)` и параметризованные
вызовы `log.info("Orders = {}, delivered = {}", count, delivered)`.
Вывод выполняет `slf4j-simple`, подключенный как runtime-зависимость проекта.
Версии API и провайдера заданы совместно в `pom.xml`.

Настройки находятся в `src/main/resources/simplelogger.properties`:
уровень INFO, время, имя потока и короткое имя логгера. В сообщениях о доставке также видно,
какой `notification-*` worker выполнил работу. Email и телефон клиента в лог не выводятся.
Бизнес-операции выполняются отдельно от вызовов логгера, поэтому изменение уровня логирования
не меняет поведение покупок.

SLF4J — фасад; провайдер отвечает за фактический вывод. На следующем занятии провайдер можно
заменить конфигурацией логирования Spring Boot, сохранив вызовы SLF4J в коде.
Справка: [официальное руководство SLF4J](https://www.slf4j.org/manual.html).

## Проверки

`mvn verify` выполняет 27 JUnit-тестов:
модели, деньги, коллекции, каталог, фильтры, атомарность многоместной покупки,
100 конкурентных клиентов, 50 одинаковых повторов, уведомления/retry/ошибки
и согласованность локального дня афиши с тестовым каталогом.

Тесты используют фиксированный Clock, настоящие потоки, стартовые барьеры, futures и Conditions.
Результат не доказывается случайными Thread.sleep. Небольшой sleep есть только в рабочем backoff доставки.
Все проверки работают с Java-сервисами напрямую. Тесты находятся в `src/test/java`:
пакет model проверяет модели, service — покупку, каталог и уведомления, CinemaDemoTest — демонстрацию.
Классы, конструкторы и методы любого уровня доступа снабжены короткими JavaDoc на русском с описанием параметров.
